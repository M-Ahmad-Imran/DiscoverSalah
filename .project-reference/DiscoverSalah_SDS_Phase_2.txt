Abstract and document history
Abstract
DiscoverSalah helps worshippers and travelers find participating mosques, mosque-specific Jama’at times and realistic walking or motorcycle arrival estimates. Its operating model combines Local Representative submissions with Focal Person approval after a call to the registered Imam. Whole City search supports longer Friday and Eid journeys. Missing-mosque suggestions and contributor applications expand coverage through controlled onboarding; a limited notice board supports verified community announcements.
The proposed solution is a modular, layered web application backed by MongoDB. Immutable schedule submissions, scoped authority, explicit pending states and atomic review decisions protect timing integrity. A provider adapter makes routing replaceable and allows honest timetable-only operation when route evidence is unavailable. The intended result is an implementable, testable service design; no code, field accuracy, interview result or deployment is claimed as completed.

1.3 Component Overview
Use a client–server, layered modular monolith: React presentation, Node.js/Express application services and MongoDB repositories. Deploy a small background worker from the same codebase for durable notifications. The first 2–3 areas use this small deployment; extract modules only if measured demand warrants it.
The browser uses public read endpoints anonymously and authenticated management endpoints for changes. Map tiles may load directly under provider terms; secret routing credentials stay on the server. The API commits domain changes and an outbox event together. The worker delivers in-account notifications after commit. No phone-call automation is implied by any connection.

Design decisions
Use a single origin for the website and /api proxy where feasible. Management access uses opaque server-side sessions in Secure, HttpOnly cookies, with SameSite protection and anti-CSRF checks on mutations. Current assignments, rather than long-lived role claims, determine permissions. Admin requires an additional factor. Exact hosting and recovery-delivery providers are selected before deployment.
Do not introduce Redis, a dedicated broker or city-wide live route precomputation in the pilot. Bound query sizes and route batches first. Any later cache must recheck schedule revision and eligibility before serving a positive label.
Controllers remain thin. Domain services receive a typed actor context and explicit command/query objects. Repositories expose conditional writes, not unrestricted collection access. Public serializers are allowlists; private phone numbers and verification notes are never accidentally removed only at the UI layer.

3.2 Data Flow Description
Figure 3  Public discovery data flow and privacy boundary
A request supplies an origin only when the user chooses personalized travel estimates. Nearby filters use an entrance GeoJSON point and the proposed 5 km default / 7 km maximum. Whole City filters explicit city membership and ignores that cap. City-wide mode still shows only participating venues; it never claims complete mosque coverage.
The resolver selects the effective approved schedule for the requested local date, applies dated exceptions and cancellation exclusions, then evaluates freshness and pending scope. Route estimates are requested for a bounded displayed batch. Recheck the applicable schedule revision before labeling; a concurrent update invalidates an older calculation. Public responses contain only the effective public values and understandable evidence status.
Management write path
Validate the current assignment → validate command → compare expected revision → write target version, review task, audit and outbox atomically → return submission status. A reviewer calls the Imam outside the system, records the outcome, and decides that exact version. Notification delivery failure does not roll back a valid submission or grant approval.
3.3 Management data flow
Figure 4  Management commands, manual verification and publication boundaries
Representatives submit proposals; the worker delivers notifications; only a scoped independent reviewer can publish the exact verified version. Domain state, audit and outbox are one transaction. Manual Imam verification is outside the software boundary and does not require an Imam account.

Figure 5  Core domain objects with attributes, operations and multiplicities
ScheduleHead is the concurrency boundary for one venue. It references zero or more immutable ScheduleVersions and records the pending proposal and approved effective windows. Design invariant
A full snapshot may include several prayer changes, but pending suppression is computed from the actual difference against the applicable approved baseline. An Asr-only change cannot suppress an unchanged Maghrib session. One active submitted schedule proposal per venue is a deliberate pilot simplification; a new full proposal supersedes the old one and recomputes the affected scopes.

4.3 Sequence for timing submission
Figure 7  Durable submission and in-account notification
A successful submit returns 202 with the immutable version and review-task IDs. Within the same transaction, the ScheduleHead revision advances and affected pending scopes become visible. The worker can retry delivery without duplicating the recipient notification. A conflicting expected revision returns 409 and requires reloading; never overwrite silently. 4.4 Sequence for phone approval
Figure 8  External Imam call followed by an exact-version decision
The registered phone number is visible only to the scoped reviewer. A confirmed call is necessary under the proposed publication policy; an unreachable or disputed outcome cannot publish. A recorded call outcome is staff evidence, not telecom proof. Revalidate target state and revision inside the transaction. An approved future schedule is selected only at its effective time. Initial mosque registration follows the same decision pattern, with publication blocked until its initial schedule is also approved.
4.5 Sequence for discovery and routing
Figure 9  Timetable results first, then bounded route evaluation
Base query order is stable by congregation time and session key. A route-evaluated batch may be re-ranked by eligibility, freshness, duration, start time and stable key. Mark the result as ranked within evaluated results; do not imply a global shortest journey when only one page has routes. Keep a stable base cursor so changing route order cannot skip or duplicate subsequent pages. A provider timeout or unsupported mode leaves timings usable and reachability unavailable.
4.6 Sequence for contributor appointment
Figure 10  Application review before invitation or authority
Only Admin can approve a Focal Person appointment. A representative appointment may be processed by Admin or a Focal Person within their area, following the Admin-reviewed application path. Check contact ownership, independent mosque reference, existing assignments and availability. Use a single-use invitation; approval alone does not expose a reusable password. Waitlist/rejection creates no management account. A private tracking token provides limited applicant status without exposing review notes.
4.7 Sequence for community notices
Figure 11  Verified and expiring community notices
A death/Janazah notice requires an authorized family or mosque source, recorded privately, before approval. The public notice needs only necessary details, actual venue, date/time and expiry. A submitted material correction or cancellation immediately marks the affected notice under review and hides its disputed event details until decided. Routine facility facts remain separate. No notice enters travel reachability unless a later scoped change introduces verified structured Janazah sessions.
4.8 Sequence for reassignment
Figure 12  Current assignments revoke old editing rights immediately
Every protected request loads the active assignment. A removed representative cannot continue using an old session or a cached role claim. Reassignment does not rewrite old authorship or silently approve pending versions. Review tasks route to the new responsible area reviewer; in-progress decisions recheck authority at commit. A venue without a maintainer becomes Maintenance pending and loses positive reachability eligibility.
4.9 State diagrams
Figure 13  Schedule submission states
A returned/rejected submission stays immutable; correction creates a new draft and version rather than editing review history. Superseded describes an undecided proposal replaced by a newer submission. Approved versions remain in history even when a later approved effective window takes over. Approval and effective activation are separate concepts; the resolver selects by time rather than relying on a precise worker tick.
4.9.1 Notice state diagram
Figure 14  Notice lifecycle, material corrections and time-based visibility
Expiry is enforced in the read query even if a cleanup job has not run. Correction creates a new pending version, and cancellation is an explicit audited disposition. A submitted change can suppress public event details without being mistaken for approved replacement content.

4.10.1 Reachability rules and ranking
Figure 16  Arrival classification and deterministic ranking within an evaluated batch
Use server-aligned departure time (or an explicitly labeled future forecast). Margin = session start − departure − route duration − preparation − uncertainty. 5 Database Design
5.1.1 ER Diagram for identity and venues
Figure 21  Identity and venue references in MongoDB
These are logical ER diagrams over MongoDB collections, not relational tables or enforced SQL foreign keys. PK means _id; REF means a service-validated reference. Each relationship joins a child reference to its parent; endpoint labels give multiplicity (0..1 optional, 1 required, 0..* many). An Assignment targets exactly one area or one venue; area assignments support Focal Persons, venue assignments support representatives. Admin has platform scope without a fabricated area assignment.
A city contains areas; each venue belongs to one area and one explicit city. The service checks city consistency. A prayer ground is a venue with type=PRAYER_GROUND, its own entrance and an optional parent mosque. PrivateContact keeps contact history; at most one contact is current for a venue. Changing the current contact requires independent verification.
5.1.2 ER Diagram for schedules and review
Figure 22  Schedule aggregate and review evidence
A venue has at most one ScheduleHead. Every submitted ScheduleVersion belongs to it and is immutable. approvedWindows references approved versions with nonoverlapping effective intervals. A ReviewTask uses a typed target: venue registration revision, schedule version or notice version. The diagram shows the schedule case; targetType prevents interpreting an ID as a different collection.
An unchanged rule copied into a new snapshot preserves its prior confirmation provenance; approving one changed prayer must not make every unchanged prayer newly phone-verified. Scope provenance references the originating confirmation and rule hash. Confirmations distinguish representative unchanged-checks from Imam phone checks and identity verification. They target an exact version and applicable scope; a later unchanged confirmation cannot clear pending changes, dispute or expiry. Public freshness is computed for the selected effective session, not from an unrelated mosque edit.
5.1.3 ER Diagram for community workflows
Figure 23  Community content and controlled onboarding
A suggestion may eventually link to an existing or newly verified venue. Each application may link to at most one approved account; several historical applications may resolve to the same account without creating duplicates. An account may also originate through a management invitation. Duplicate applications are resolved without duplicating accounts. Notices and issue reports reference existing venues; reports may reference a logical session key without requiring a stored occurrence document.
Supporting collections are AuthSession, AccessToken, OutboxEvent, Notification, AuditEvent and IdempotencyRecord. They reference Account or typed domain targets and are defined below. The following operational panel makes these support relationships explicit; their detailed fields and indexes appear in Section 5.2.5.
5.1.4 ER Diagram for operational records
Figure 24  Authentication, inbox delivery, audit and idempotency relationships
AuthSession and AccessToken share the account relationship but remain separate collections with different lifecycle rules. Notification eventKey links to the durable outbox event, while recipientId links to Account. Audit actorId is optional for system actions. Idempotency actorKey can identify an authenticated account or a scoped public submission; it is not always an Account foreign key. Typed domain targets are validated by the application.

5.2.3 Embedded schedule structures
Structure
Fields and validation
RecurringRule
ruleId:str; prayer:enum; weekdays:int[]; localTime:HH:mm; fromLocalDate:YYYY-MM-DD; untilLocalDate?:date; sermonTime?:HH:mm. Valid date range and one unambiguous effective rule per prayer/session.
DatedSession
sessionId:str; prayer:enum; localDate:date; localTime:HH:mm; venueId:oid; dateStatus:CONFIRMED|PROVISIONAL; canceled:bool; supersedesRuleId?:str; sermonTime?:HH:mm. Multiple Friday/Eid sessions retain distinct IDs.
Exclusion
localDate:date; ruleId or sessionId:str; reason:str. Cancellation explicitly suppresses matching recurring fallback. Deleting a dated row is not a cancellation.
AffectedScope
prayer:enum; fromLocalDate:date; untilLocalDate:date; ruleIds/sessionIds:str[]. Computed from approved-versus-proposed values. Full-venue suppression only for identity/maintenance problems.
Logical session key
venueId + localDate + stable ruleId/sessionId. scheduleRevision is a separate concurrency field; it does not create a new logical prayer simply because metadata changes.
ResolvedSession value
logicalKey, prayer, startAtUTC, localDate, venue/entrance, scheduleRevision, sourceVersionId, confirmation timestamps, timingStatus and reasonCodes. Derived on request; no persisted occurrence collection required for the pilot.
Date, cancellation and Friday rules
Convert the explicit local date and time in Asia/Karachi to UTC for comparisons. Reject ambiguous prayer/date combinations and past future-planning departures. Keep sermon time separate from Jama’at start. Eid date confirmation changes require a reviewed version. A canceled dated event stays excluded even if a recurring rule would otherwise match. Do not silently replace selected Asr with Maghrib.
Submission simplification
Keep one active schedule proposal per venue. A representative editing while a proposal is pending submits a new full snapshot against the current head revision. The service supersedes the old proposal, replaces its task and recalculates all pending differences. A reviewer holding the older version receives 409. Future parallel per-prayer proposals require a separate concurrency design.

5.3 Transactions and concurrency
Command
Atomic changes
Submit schedule
Compare ScheduleHead revision; supersede prior pending proposal/task; insert immutable version, new task, audit and outbox; advance head and affected scopes.
Approve schedule
Recheck assignment and exact submitted target; write evidence/decision; update approved windows and pending scope; increment revision; append audit/outbox.
Approve registration
Verify scoped actor, contact and registration revision; publish approved venue snapshot only with an approved initial schedule; append audit/outbox.
Approve application
Write reviewed decision; create or link disabled/invited account; create scoped invitation and proposed assignment; audit/outbox. Activate only after invitation acceptance.
Reassign maintainer
End current assignment, activate replacement, adjust maintenance status and review ownership, append audit/outbox.
Deploy MongoDB with transaction support on a replica set. Keep transactions short and retry only documented transient conflicts; avoid external calls inside them [R2]. Conditional revision writes are the guard against concurrent approvals. If a duplicate submit is retried, idempotency returns the original logical result. A failed transaction leaves neither a published change nor a half-created review notification event. Protected writes also conditionally touch the current Account and Assignment revision guards inside the transaction; deactivation/reassignment writes the same guards. This prevents a concurrent revocation from being bypassed by a stale authorization read.
Read consistency
Only a scoped reviewer can confirm a report as a timing dispute and set ScheduleHead.disputedScopes; the report alone never changes public facts. Increment head revision on dispute, clearance or maintenance-status change. Read ScheduleHead and the referenced immutable version coherently. Immediately before returning positive reachability, confirm the head revision has not changed; if changed, resolve again once or return refreshing/unavailable. At future-window boundaries, resolve using current server time on every read. Polling within the SRS 60-second target refreshes active clients; foreground resume refreshes immediately.
Provider and privacy boundary
Do not persist precise anonymous origins by default. Route requests use POST bodies to avoid URL query logging, and request logging must redact coordinates. Provider disclosure and short-lived in-memory processing are documented to users. No route cache retaining personal origins is required for the pilot.
6 API Design
6.1 Shared contract rules
Base path: /api/v1. JSON dates/times are ISO 8601 UTC except explicitly named localDate/localTime fields. Opaque IDs are strings on the wire. Return requestId and serverTime in every response. Success: {data, meta}; failure: {error:{code,message,fields?}, requestId}. Never expose internal stack traces or private evidence through public DTOs. Contracts below are proposed implementation interfaces, not running endpoints.
Rule
Contract
Pagination
Cursor plus limit (proposed default 20, maximum 50). Base session query has stable startAt/logicalKey ordering. Include nextCursor and coverage information.
Concurrency
Protected mutations require expectedRevision or If-Match. A stale target returns 409 VERSION_CONFLICT with a safe reload instruction.
Idempotency
Submission and decision POSTs require Idempotency-Key. Retry identical requests safely; key reuse with different content returns 409.
Authentication
Opaque secure cookie session for management routes; CSRF token and Origin checks for cookie-authenticated mutations. Public browsing needs no account.
Validation
400 malformed; 401 missing/expired auth; 403 scope denied; 404 absent or concealed object; 409 conflict; 422 domain validation; 429 rate limited; 503 dependency failure when no useful fallback exists.
Routes

Public forms
202 receipt includes reference and high-entropy private status token. Tracking token is sent in POST body; public reference is not authorization.
