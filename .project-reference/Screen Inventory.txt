Screen Inventory “DiscoverSalah”
For DiscoverSalah, I recommend one responsive website with four experiences: Public Discovery, Local Representative, Focal Person, and System Admin. Shared screens should adapt to the person’s permissions.
Below is a comprehensive screen inventory for the documented product. A page, tab, form, and dialog are different design deliverables—not every item needs a separate URL. Items marked Conditional require a scope decision; Recommended items are supporting UX additions.

8. Essential states and dialogs
These must appear in the design files and testing plan. Most are states within existing screens.
State or dialog
Required experience
Location permission denied
Offer manual location/pin selection immediately.
Origin not selected
Allow timetable browsing; explain why personal travel estimates are absent.
No participating mosques
Explain the coverage gap and offer suggestion/contributor actions.
No matching upcoming sessions
Retain selected prayer/date; offer explicit filter changes without silently switching prayer.
Travel estimates loading
Keep timetable results visible while estimates load.
Route unsupported or unavailable
Show timings and a reason; withhold a positive reachability label.
Map unavailable
Preserve list results and address information.
Partial route evaluation
Identify which results have been evaluated; avoid claiming a global shortest-journey ranking.
Offline / connection lost
Identify potentially stale content and stop live reachability claims.
Timing under review / stale / disputed
Explain the specific affected session and why confidence is reduced.
Provisional Eid date
Keep planning information visible with a clear provisional label.
Session started or canceled
Remove it from upcoming recommendations and explain its status on a directly opened detail page.
Maintenance pending
Retain useful location information while clearly limiting timing confidence.
Version conflict
Explain that someone submitted a newer version; require reload and renewed review.
Imam unreachable
Record the attempt, retain pending status, and provide follow-up/escalation.
Possible duplicate
Show potential matches before creating another record.
Validation error
Give field-specific instructions while retaining safe entered information.
Unsaved changes
Confirm before leaving an edited form.
Submission outcome uncertain
Check the result before retrying; avoid duplicate proposals or decisions.
Rate limit reached
Explain when to retry without losing the user’s safe form inputs.
Expired invitation / tracking access invalid
Provide a safe recovery path without revealing private information.
Access revoked during work
Stop protected actions and explain that permissions changed.
404 / temporary service error
Provide a useful return path and retry option.
9. Features that should not become initial-release pages
Keep the following outside the initial design backlog:
Potential feature
Treatment
Subscription plans, checkout, wallet, payroll
Outside the agreed initial scope.
Donation collection or funding-organization portal
Future funding is an organizational activity; a transactional portal is not currently justified.
Imam dashboard
No Imam login is required; verification happens through calls.
Public account dashboard
Anonymous discovery and secure request tracking meet the current requirements.
Social feed, comments, ratings, public posting
Outside the limited, verified notice-board model.
In-app chat or automated phone calling
Not part of the documented verification workflow.
Native mobile onboarding/screens
Design the responsive website first.
Full-trip “mosques along my route” planner
Separate future feature; current discovery starts from a selected origin.
Janazah reachability calculator
Requires separately approved structured-session rules.
Automated WhatsApp/SMS alerts
Deferred pending a funded, verified delivery channel.
Language selection and Urdu layouts should be designed as conditional variants across the whole interface, not as a separate collection of pages.
Recommended design order
Public discovery → mosque details → session estimate → directions.
Representative timetable update → Focal Person verification → public timing refresh.
Mosque registration → approval → publication.
Reports, missing-mosque suggestions, and contributor applications.
Notices, account administration, reassignment, and operational oversight.
Start by prototyping those first two journeys end to end. They will expose the most important usability risks: whether a traveler can find trustworthy information quickly, and whether mosque staff can keep that information accurate.
